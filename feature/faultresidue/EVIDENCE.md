# Fault residue evidence record

Status: reviewed

Fault residue reads the kernel fault record that the process main thread inherited from the zygote main thread at fork, and asks whether it names a recovered instruction abort: a fault-hijack injector sends execution to an address the MMU rejects and an external ptrace resumes the process, and the kernel's one-slot record of that promoted exception survives the fork into every child of that zygote thread. A clean result here clears only this channel and only up to the sampling instant.

## Signals

### Inherited kernel fault record

- Observable signal: the current thread's `thread.fault_address` and `thread.fault_code` pair, read on the main thread at startup through a self-directed SIGWINCH: `setup_sigframe` projects the address unconditionally into `ucontext.uc_mcontext.fault_address` and stores the code in an `ESR_MAGIC` (0x45535201) record inside `__reserved` when it is non-zero.
- Producing subsystem: the arm64 kernel's fault and trap entry paths (`arch/arm64/mm/fault.c`, `arch/arm64/kernel/traps.c`), which write the pair only when an exception is promoted to a signal; `arch_dup_task_struct` (`arch/arm64/kernel/process.c`) copies it into the child at fork; `arch/arm64/kernel/signal.c` and `signal32.c` are its only user-space exits (no ptrace regset, no `/proc` field).
- Mechanism: an injector that hijacks the zygote main thread's execution flow does so by jumping to an address that faults; the promoted instruction abort (EC 0x20) writes the record, the default SIGSEGV consequence ends the process, and only an external ptrace observer can resume it. The thread then keeps that record in its single slot, every fork of that thread copies it, and the child's earliest Java-side sampling point (a ContentProvider installed between `Application.attachBaseContext` and `onCreate`, running on the main thread) reads the value the parent held at fork. SIGWINCH is non-fault, so installing a `SA_SIGINFO` handler, directing one signal at this thread with `tgkill` and reading the frame neither consumes nor alters the stored pair.
- References: kernel/common `arch/arm64/mm/fault.c` (`__do_user_fault`/`set_thread_esr` write the pair for promoted faults), `arch/arm64/kernel/traps.c` (non-page synchronous exceptions write `{0, esr}` with EC != 0x20), `arch/arm64/kernel/process.c` (`arch_dup_task_struct` copies it at fork), `arch/arm64/kernel/signal.c` + `signal32.c` (`setup_sigframe`/`setup_esr_el1_context` project it; the record is absent for a zero code), `arch/arm64/include/uapi/asm/sigcontext.h` (`esr_context`, `ESR_MAGIC`); pinned ACK 5.10 at [a3431a2d](https://android.googlesource.com/kernel/common/+/a3431a2d02cd16bb212f7839cfa0934ce2a367ff/arch/arm64/mm/fault.c) and ACK 6.1 at [31addbff](https://android.googlesource.com/kernel/common/+/31addbff5e86095b5ee63a5d6446d7e76000bbc0/arch/arm64/kernel/signal.c) implement the same write-on-promote and project-on-signal contract; `kernel/signal.c` default action table (SIGSEGV terminates). Discovery only: fault-hijack injector readings `{0, 0x82000005}` and `{page address, 0x8200000f}` observed as black-box on rooted devices with the probe APK at `C:\Users\LunOS\.workbuddy\tmp\demo3`; no injector code is copied and no injector names are stored in the verdict rules.
- Applicability: arm64 only. armeabi-v7a keeps no ESR projection and x86/x86_64 keep no fault_code field at all, so those ABIs answer `UNSUPPORTED_ARCH` from a link-time stub rather than reading a guessed layout. The inheritance chain requires the sampling thread to be forked from a zygote main thread whose record was written before a later promoted exception overwrote it: observed on one arm64 4.19 device across four kernel families (4.19/5.1/5.10/6.1 write the same contract), and the host tests exercise frame layout, not vendor kernels.
- Visibility limits: the slot is single-entry and per-thread: the last promoted exception wins, any earlier record is lost, and other threads carry unrelated records. An app cannot read the zygote's live value, only the copy it inherited, so the sampling point (the earliest Java hook, before the process produces exceptions of its own) decides what the reading means. On devices whose zygote baseline already holds a null-address data read (measured on untouched 5.1/5.10/6.1 devices as `far=0, esr` with EC 0x24 read), the injection record is overwritten before the app can fork: this channel cannot see it there, which is an explicit inconclusive, not a clean result. Injectors that fault without an external resume either end the process or do not use this path; a fault-free injection never writes the record at all, and no outcome proves absence of injection methods this probe was not designed to see.
- Result states: detected (EC 0x20 instruction abort in a live process), no record (far == 0 and no ESR record), overwritten (EC 0x24 read at address 0), unattributable (any other non-zero record), unsupported (non-arm64 link), unavailable (sigaction failed, handler silent, missing payload, library missing, no startup sample).
- Interpretation: detected means this process's inherited record shows execution sent to a rejected address whose default consequence did not end the process: an external observer caught and resumed a fault-hijack injection at some point in this fork lineage. It names neither the injector nor its payload, and stored FAR/DFSC values are injector implementation details, never criteria. No record clears only the sampled thread's channel at the sampling instant. Overwritten and unattributable are explicit non-verdicts: absence of a viewable record is not evidence of absence. The warning (not danger) severity reflects that one record on one lineage with vendor-specific overwrite behavior is corroboration-grade evidence until field data across more devices establishes otherwise.
